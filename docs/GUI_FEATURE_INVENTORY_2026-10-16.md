# Avila GUI feature inventory — 2026-10-16

This is a source-based functional inventory of the current Avila GUI, compared with the stable Bitcoin Core GUI release **31.1**. The upstream comparison is pinned to the [`v31.1` release tag](https://github.com/bitcoin/bitcoin/tree/v31.1/src/qt); the official [31.1 release page](https://bitcoincore.org/en/releases/31.1/) and [release index](https://bitcoincore.org/en/releases/) identify that release. Source links below use the immutable tag, not `master`.

## Evidence limits

This document inspects routes, actions, node models, and backend RPC dispatch. It does not assess rendered layout, visual hierarchy, keyboard usability, screen-reader behavior, or accessibility. No native GUI screenshots were available during this inventory; source cannot substitute for a screenshot-based product audit. The GUI has `--demo` and several appearance/toy modes, but those are excluded from claims about live node capabilities. See [app route dispatch](../crates/avila-gui/src/app.rs#L355) and the explicit demo/live distinction in [model.rs](../crates/avila-gui/src/model.rs#L1).

“Absent from GUI” below means no route/action or data flow was found in the live page dispatch and its source, not merely that a particular menu label was missing. “Backend ready” means the node source exposes relevant data or commands; it does not mean there is already a stable GUI-facing contract for that workflow.

## What the live GUI already exposes

The standard navigation has Overview, Chain, Peers, Activity, Config, and Settings. Toybox is conditional. The page dispatch confirms these are the live views and distinguishes the optional toy page ([rail.rs](../crates/avila-gui/src/rail.rs#L13), [app.rs](../crates/avila-gui/src/app.rs#L375)).

The classic skin adds a minimal `File`, `Options`, `Help`, and `Node` menu, start/stop and copy-tip actions, and the original Send Coins/Address Book bitmap buttons. The buttons are intentionally inert and disclose that Avila does not hold or send coins; the “Generate Coins” item is disabled. This is historical chrome, not a wallet or menu parity implementation ([classic.rs](../crates/avila-gui/src/classic.rs#L268), [classic.rs](../crates/avila-gui/src/classic.rs#L309)).

### Menu inventory in plain terms

Core 31.1’s wallet-enabled native GUI has **File** (wallet lifecycle/backup/restore, URI, sign/verify, PSBT, exit), **Settings** (wallet encryption/passphrase, value masking, Options), **Window** (minimize and debug tabs, plus wallet address windows), and **Help** (command-line options, About). These are source-confirmed menu actions; exact wallet entries depend on whether the wallet is compiled/enabled. See the pinned [upstream menu implementation](https://raw.githubusercontent.com/bitcoin/bitcoin/v31.1/src/qt/bitcoingui.cpp#L487-L571).

Avila’s normal shell exposes **pages**, not a comparable menu bar: navigation is in the rail, with start/stop in status controls and node configuration in Settings/Config. The optional classic skin has File/Options/Help/Node, but no wallet operations; its apparent Send Coins and Address Book buttons only display original bitmap assets and have explanatory hover text. This distinction matters because a screenshot of the classic skin can suggest features that do not exist.

## Block visualization: recommended scope

The highest-value addition is an **inspectable block view**, not an ornamental chain graphic. Avila already has a useful chain-level visualization: the ribbon conveys chain coverage and validation status, while the overview shows a fee staircase for the prospective next block. Neither answers “what is in this block?”

Recommended sequence:

1. Make each recent connected block open a detail view. Start with the block hash, height, timestamp, previous hash, version/bits/nonce, transaction count, serialized size/weight, coinbase output/subsidy, fees when computable, and a transaction table. Put retrieval state and data coverage beside the block: **validated active-chain block**, **header only / body pending**, **body unavailable because data is pruned**, or **not on the active chain**. The existing `connected` and `headers` heights provide the initial distinction, and `getblock`/`getblockheader` provide block data.
2. Add an optional composition view for a fetched block: transaction fee-rate bands or a sorted treemap by weight, with coinbase distinguished; clicking a cell opens transaction inputs/outputs and fee/weight facts. Provide a sortable table and text details as equal access paths. Label measured block data separately from the live mempool’s **next block estimate**.
3. Add height/hash search and adjacent-block navigation. Fetch off the paint thread, cap concurrent requests and displayed rows, and state when historical details depend on retained block files or optional indexes.
4. Only add branch/reorg visualization once the node provides branch identity, active-chain membership, and reorg events with defined retention. A line between heights or a color change inferred from recent-tip movement would be misleading. Show best-header candidates and active validated chain separately; snapshot-assumed coverage remains distinct from replay-proven coverage.

For any future timeline, chart or block glyph, preserve the repository’s own GUI requirements: measured source, explicit unknown/stale/disconnected states, text/keyboard alternatives, and separate meanings for header acceptance, active-chain connection, script validation, snapshot assumption, and local mempool policy ([docs/GUI.md](GUI.md#acceptance-requirements)).
