**Codex audit of SWE-2 experiments 72–75**

Date: 2026-09-26. The accepted target is maintained in
[IBD_PRODUCT_OBJECTIVE.md](IBD_PRODUCT_OBJECTIVE.md): first launch to full
Bitcoin validation within one hour on the reference laptop, under specified
connection conditions.

This review inspected the implementation, reports, saved JSON/log files, and
already-built benchmark binaries. It recomputed statistics from existing
samples and re-extracted assembly instruction counts. It did not run a new
benchmark, replay, corpus scan, or live-node operation. File hashes and the
derived statistics are in
[the review evidence](evidence/2026-09-26-ibd-swe2-review-72-75.json).
The experiment reports remain the original author's record; the acceptance
status and required corrections below supersede their stronger conclusions.

**Disposition**

| Experiment | Supported result | Gate still open |
| --- | --- | --- |
| 72, census | Structural counts over selected real block files; an explicit SegWit-era gap | Correct hash accounting, matched executed calibration, representative history, reproducible uncertainty model |
| 73, SHRD | Staged binaries reduce SHRD sites; saved timing samples favor the candidate in aggregate; synthetic advice timing is recorded | Reconcile report/statistics, broaden arithmetic correctness, measure representative multicore receiver capacity and helper cost |
| 74, replay | Reported parallel script execution on fully resolved selected transactions | Repair source identity and coinbase coverage; distinguish resolution from execution; include preparation cost and matched worker-pool baseline |
| 75, state | Existing ledger sizes and join JSON describe sampled record volumes and set overlap | Implement occurrence-aware state predicates and exact materialization; establish a closed comparison boundary |

These are useful partial deliverables. They do not establish a physical CPU
floor, a replacement for serial consensus-state handling, or a complete exact
UTXO join implementation.

**1. Correct the floor statement before using it for decisions**

The reported 2.3–4.9 hours comes from:

```
assumed attempts:                  1.65 billion to 3.5 billion
best synthetic receiver time:     40.265 microseconds per attempt
assumed perfect CPU parallelism:  8 cores
time = attempts * receiver_time / 8
     = 2.307 to 4.893 hours
```

The arithmetic is valid under those assumptions. The workload interval is not
an exact or statistically established whole-history bound; the fastest timing
is a synthetic all-valid ECDSA receiver sample; eight-core scaling of that path
was not measured. Schnorr and early-exit/cached cases are not priced by the
same ECDSA routine. Preparation, helpers, hashing, and state are also outside
that simple calculation.

Required wording:

> Under the provisional workload range and ideal eight-core scaling, the best
> tested synthetic advice-assisted ECDSA receiver path projects roughly
> 2.3–4.9 hours for that modeled signature workload alone. This implementation
> does not meet the one-hour target. These measurements do not establish the
> fastest possible implementation on this CPU.

Remove “unreachable on this CPU,” “GPU/cluster required,” “measured interval,”
and “physical floor” as descriptions of this calculation. A measured algorithm
provides evidence about its performance, not a lower bound over every possible
algorithm and machine schedule. Keeping the target does not establish that an
as-yet-unbuilt faster CPU path exists either.

The size of the remaining gap is actionable:

| Provisional attempts | Sustained attempts/s for one hour | Ideal per-attempt CPU time with all 8 cores | With 6 signature cores |
| --- | ---: | ---: | ---: |
| 1.65B | 458,333 | 17.45 microseconds | 13.09 microseconds |
| 3.5B | 972,222 | 8.23 microseconds | 6.17 microseconds |

The 40.265-microsecond sample corresponds to approximately 198,683 attempts/s
under ideal eight-core division: another 2.3–4.9x would be needed for the
signature portion under the same workload assumptions. This is a substantial
unproven improvement, and other validation work needs resources too. These
rows are requirements, not achieved rates or confidence bounds.

Also correct the storage/network passage in experiment 72. PCIe 3.0 x4's
coding-only bandwidth ceiling is not measured SSD read throughput and cannot
exclude storage as a bottleneck. The 768 GB raw-transfer calculation at
1 Gbit/s is 102.4 minutes before overhead; any larger estimate needs explicit
overhead/goodput assumptions. It is not derived from “1 Gbps” alone.

**2. P1: the corpus resolver drops file identity**

In [`ibd_corpus_window.py`](../tools/ibd_corpus_window.py), the index occurrence
contains `(height, tx_index, file_index, record_offset, tx_offset, tx_length)`.
At line 259, however, the emitted lookup specification becomes only
`(record_offset, tx_offset, vout)`. `resolved_map` uses that same shortened key
at lines 263–287 while loading multiple files.

Offsets are local to each file. Different files can contain different source
transactions at identical record/transaction offsets. One entry can overwrite
another and return the wrong output. The later dictionary lookup no longer
checks the requested source txid. This is a source-derived correctness defect;
this audit did not establish that the saved sample encountered a collision.

Carry file identity or a globally unique occurrence identifier through every
lookup and into auditable provenance. Recompute the selected source txid and
assert that the referenced index/output matches the spending outpoint before
accepting its metadata. Add a tiny deterministic multi-file collision test
before generating a larger corpus.

**3. P1: coinbase coverage and occurrence validity are incomplete**

The index loop at lines 204–205 explicitly skips coinbase transactions with
the comment “not a spendable source class.” Coinbase outputs become spendable
after the applicable maturity interval; see
[`COINBASE_MATURITY` and connect checks](../crates/avila-consensus/src/connect.rs).
Excluding them makes valid inputs unresolved even when their sources are
already in the files. The current binary format stores only `TxOut` data and
does not carry creation height/coinbase status as source metadata.

Index coinbase outputs, retain their identity and creation position, and check
maturity separately from availability. Report excluded/unresolved classes
explicitly. The current “older than the source span” explanation cannot be
assigned to every unresolved input.

Choosing the latest earlier txid occurrence is a useful resolution step, but
does not prove the earlier output was unspent, that a duplicate creation was
permitted, or that the block is on the selected chain. The manifest reports
zero duplicate txid occurrences, so this sample did not exercise that case.
[BIP30](https://github.com/bitcoin/bips/blob/master/bip-0030.mediawiki) imposes
conditions on duplicate transactions and includes historical exceptions; a
dictionary choice does not implement those rules.

Use a chain-identified block/height map. A coinbase-encoded BIP34 height is not
a general height source for earlier history or a proof of ancestry. File
records may be gapped or from different branches, and the tool sorts records
within individual files rather than establishing a global selected chain.
Preserve the explicit distinction between a trusted test corpus's provenance
and a first-launch validator's verification of untrusted data.

**4. P1: zero script failures do not authenticate all prevout metadata**

Experiment 74 says any wrong script or amount would break sighash. That is
false for the pre-SegWit window being tested: legacy signatures do not commit
to the spent amount. This difference is explicitly described in
[BIP143's motivation](https://github.com/bitcoin/bips/blob/master/bip-0143.mediawiki).
Some valid scripts also impose no signature condition that could authenticate
arbitrary supplied metadata.

`check_input_scripts` accepts the caller-supplied outputs; it does not resolve
the actual outpoints or perform state availability, double-spend, value/fee,
maturity, or block reward checks. Zero failures are evidence about the scripts
executed with the supplied data. They cannot substitute for source identity,
amount equality, state predicates, or an exact chainstate comparison.

Add regressions demonstrating these separate contracts: a changed legacy
prevout amount must be caught by provenance/state validation even where script
verification still succeeds; fabricated permissive scripts must not authorize
a fabricated source. Keep script and state validation outcomes separately
observable.

**5. Experiment 74 executed 76.8% of inputs, despite 89.1% resolution**

The manifest and reported run describe different denominators:

- Total non-coinbase inputs in the selected file: 671,771.
- Individually resolved inputs: 598,267, or 89.06%.
- Inputs in fully resolved transactions actually replayed: 515,779, or 76.78%.
- Resolved inputs dropped because another input in their transaction was
  unresolved: 82,488.

[`corpus_replay.rs`](../crates/avila-consensus/examples/corpus_replay.rs)
skips a whole transaction when any prevout is missing, but
`skipped_unresolved` counts only missing outputs (including coinbase markers).
It does not report all excluded non-coinbase inputs. This creates selection
bias, particularly for larger or older-source transactions.

Fix the counters: total transactions/inputs, missing-source inputs, resolved
inputs in excluded transactions, executed transactions/inputs, attempted
ECDSA/Schnorr backend calls, early exits, and failed transactions/inputs.
`done += n_in` is an input count, not a dynamic signature-attempt count. On a
failure, `check_input_scripts` can return before visiting all inputs, while
the current counter still credits all of them and the process exits normally.
Preserve partial diagnostic output but return a failing run status when the
declared correctness criterion is not met.

Preparation happens before the replay timer: source indexing, extraction,
reading the whole binary, parsing, transaction decoding, and task allocation
are excluded. Report those stages and peak memory separately, then report the
combined cost when comparing architectures. The script timer is useful as a
component measurement.

449 records across heights 340,787–342,234 are not a contiguous 1,448-block
window. The manifest's ten source files contain 3,660 records. Missing sources
can be gaps, omitted coinbases, or older history. Do not infer ages without
complete coverage or independently resolved source heights.

The reported 4.56x scaling is a shared-host observation. No counters establish
whether its flattening is kernel throughput, scheduling, memory, or queue
coordination. The asserted quiet-host 6–7x is an untested forecast. Compare
against the existing script worker pool on identical transactions and matched
resources before claiming an architectural throughput improvement. Keep
“parallel script replay works on this subset”; withdraw “serial connect is
dead.”

The saved manifest supports resolution totals. The indicated build log contains
those totals, while the cited worker timing rows are in the report. Preserve
the original replay JSONL, stderr, exit status, command/build hashes, and resource
conditions alongside the next run so the scaling can be independently audited.

**6. P1: repair hash-work accounting before extrapolating it**

The census labels its sighash totals as structural estimates, which is
appropriate. The summary promotes those estimates to measured SHA input and
whole-chain resource bounds, which the implementation does not support.

In [`ibd_census.py`](../tools/ibd_census.py), lines 289–291 charge the full
stripped transaction size for every non-witness input. Actual legacy sighash
serialization in
[`write_legacy_sighash_preimage`](../crates/avila-consensus/src/sigchecker.rs)
blanks other inputs' scripts and supplies the current `scriptCode`, with
additional changes for the hash type. One input can cause zero, one, or
multiple executed verification/hash attempts, and caches can avoid repeated
work. The census formula neither counts those events nor reproduces their
preimage bytes. It can substantially overstate common legacy preimages.

Legacy hashing amplification is a legitimate issue to investigate, but the
quoted 9–11 GB and 35–75x figures are estimates from that formula, not counted
executed SHA input. They must be regenerated or clearly labeled as a coarse
model without a demonstrated error bound.

Additional accounting issues:

- The stripped length subtracts witness payload bytes and marker/flag but
  retains witness stack-count and item-length encodings. That is not the exact
  stripped serialization length for SegWit transactions.
- Every witness input receives a constant five SHA compressions. That does
  not account for variable scripts, executed paths, BIP143 shared components,
  Taproot tagged hashes, or cache reuse.
- Every transaction receives a wtxid hash count, even where no witness
  commitment is applicable or a txid result is reusable. It is not a minimum
  necessary hashing count.
- Merkle interior count is approximated by `n_tx - 1`, which omits the actual
  odd-level duplication work. The calculated `tx_hashes` use full transaction
  bytes and are not checked against `merkle_seen`; neither variable becomes
  a Merkle-verification step.
- Counting 64/65-byte witness items as Schnorr-sized is a shape statistic,
  not confirmation of a Schnorr verification. Script/control/other data and
  executed signature operations must remain separate categories.

Instrument actual preimage lengths, compression calls, executed signature
attempts, and reuse at the real code boundaries. Cross-check those counters
against exact serialization on small known cases, then calibrate structural
counts on the **same** identified blocks and inputs. The documented structural
samples and 24-block trace cover different height ranges; no linked matched
calibration establishes a whole-history 4% error bound.

The whole-history model also needs repair. `ibd_workload.py` applies the first
501 blocks' sparse density to all heights through 227,930, extrapolating only
about 4,550 non-coinbase inputs in that entire interval. That is not a
representative sample of those years. It applies the late Taproot slice to the
whole Taproot era, buckets a mixed-height file by its median, and hardcodes an
endpoint of 970,000 instead of a pinned benchmark tip.

The saved `workload.json` has no rate/deadline table or implemented low/high
range generator despite the report's reference to such rows. Its measured-era
point extrapolations already sum to approximately 2.391 billion inputs before
the unmeasured SegWit era. The prose's 1.6–3.4B interval may represent other
assumptions, but they are not reproducible from this artifact. Encode every
range assumption, distinguish scenarios from statistical bounds, and label
unmeasured eras as unknown rather than a demonstrated bounded interval.

**7. P1: the current state join is set overlap, not exact chainstate**

[`ibd_state_ledger.py`](../tools/ibd_state_ledger.py) emits fixed-size records,
then builds `created[(txid,vout)] = height` and a set of spent keys. At join
time it discards spent heights and all multiplicity. It never invokes the
occurrence resolver. The report's claim that maturity and BIP30 are accounted
for by that resolver is therefore unsupported.

Consequences visible from the implementation:

- Duplicate spends collapse to one set entry. The diagnostic
  `len(spent_keys) - in_span - outflow` is identically zero because
  `in_span = len(spent_keys) - outflow`; it cannot detect duplicates.
- A spend can match a later-created output because ordering is not checked.
  Same-block transaction order is absent from the ledger.
- Duplicate creations overwrite each other in the dictionary. Earlier
  occurrence spends can erase later occurrence survivors.
- Coinbase identity is not retained per output, and no maturity predicate
  runs. A total coinbase-output counter does not supply that information.
- The created ledger omits scriptPubKeys and source locators for recovering
  them. The survivor list retains only keys/heights and is not emitted as a
  complete usable chainstate. Provably unspendable outputs are counted, while
  ordinary connect excludes them.
- Input/output value rules, per-transaction fees, block subsidy/reward, and
  lock/sequence constraints are not established by this join.

The 77.2% number can describe overlap of the selected created/spent key sets.
It does not independently prove an exact-state algorithm or a whole-history
survivor fraction. The 16% absent-source class cannot all be called older
history when input files are not demonstrated to cover a contiguous chain
interval. Call it “source absent from selected records” until independently
resolved.

The existing file sizes are consistent with 7,241,145 records of 48 bytes and
6,656,451 records of 40 bytes. `target/ibd-ledger/341k/join.json` contains the
reported summary. The accompanying `target/ibd-ledger-341k.log` records an
earlier 44/48-byte parsing failure; the current script writes `ledger_result.json`,
which is absent at that indicated location. Preserve a successful command,
source manifest, format version, output hashes, and exit log to connect the
reported join to a reproducible execution. Do not erase the failed run.

The 614 MB covers ledger writes, not complete external-join traffic. Input
scans, partition/sort passes, reads, temporary files, metadata, script recovery,
and durable survivor output need their own measurements. Likewise, extrapolated
20–25% survivors and an 8 GB exact UTXO output are not established by this
fixed-record sample.

**8. Experiment 73: retain the candidate, tighten the evidence**

Re-reading the staged binaries with `objdump --no-show-raw-insn` confirms
`fe_mul_inner` and `fe_sqr_inner` each contain eight SHRD instructions in the
vanilla binary and one in the patched binary. No benchmark was executed for
this check. The supplied `disasm_census` JSON incorrectly records zero for all
listed instruction mnemonics: its parser matches raw byte columns. Fix that
parser and make impossible all-zero instruction results fail loudly.

Recomputed from the current saved `results.json`, using all 18 pass samples
per variant and mode:

| Mode | Vanilla median CPU time / 2048 records | Patched median | Reduction |
| --- | ---: | ---: | ---: |
| compressed parse + verify | 0.193295 s | 0.182924 s | 5.37% |
| preparsed verify | 0.169977 s | 0.164503 s | 3.22% |

The report gives different aggregate medians (4.2% and 2.8% reductions).
Reconcile the report with the exact hashed result artifact. Eighteen passes
come from six process invocations per variant, not eighteen independent process
runs. Two of the six paired process comparisons regress slightly in each mode.
Preserve paired results and a specified statistical method; do not convert
the most favorable minimum into a general expected gain.

This is enough to keep a small optimization candidate. It is not a full-node
win or an instruction-latency measurement. Aggregate A/B timing alone does
not identify SHRD's marginal cycle cost or prove that out-of-order execution
is the cause of the small improvement. Describe that explanation as an
inference unless measured counters or a stronger dependency analysis support it.

The advice logs do reproduce the synthetic comparison:

- Vanilla ordinary: 94.447 microseconds per signature, median of two runs.
- Patched `batch_y33`: 40.265 microseconds, from 38.513 and 42.017.
- Ratio: approximately 2.35x for this receiver calculation.

There are 4,096 synthetic records, so requested batch size 8,192 does not
demonstrate an actual 8,192-record batch. The advice producer runs before
receiver timing; the patched producer alone reports approximately 91.4
microseconds per record. Count that cost if the receiver generates advice
locally. If a remote source supplies it, count helper transfer, authentication,
coverage, and any fallback work instead. For a nominal 33 bytes per attempt,
the provisional attempt range means 54.45–115.5 GB of helper data before
additional framing or encoding. Report the tradeoff against smaller advice
formats rather than choosing solely by the fastest receiver kernel.

No whole-history claim follows from a uniform-valid synthetic workload. Retain
the correct slow path, test malformed/false/rare cases and arithmetic boundaries,
and run the pinned library's appropriate tests before integrating a dependency
change. Measure the patched advice path on representative executed traces and
then on a quiet multicore host. Leave production integration to the agreed
code owner.

**9. Revised next assignment to SWE-2**

Keep the one-hour product objective. Complete the following gates in order;
do not start by scaling the current resolver to a much larger Python index.

1. **Repair the small correctness defects first.** Carry complete source
   identity through the resolver; index coinbase outputs; attach and verify
   creation/chain metadata; correct the census serialization counts and
   disassembly parser. Add deterministic regressions for cross-file offset
   collisions, mature/immature coinbase sources, missing/gapped sources, and
   duplicate occurrences. These are research-tool repairs, not authorization
   to change consensus rules or bypass checked-state handling.
2. **Make the measurements self-accounting.** Preserve replay JSONL/exit logs,
   return nonzero on unexpected script failures, reconcile every denominator,
   and add actual ECDSA/Schnorr/sighash counters in an isolated consensus
   build. Calibrate structural counts on the identical executed transactions.
   Split pre-BIP34 history into defensible samples; acquire a bounded SegWit
   sample and pin the tip. Emit reproducible range assumptions and requirements
   in the JSON instead of a prose-only floor table.
3. **Close one state window exactly.** Use an explicitly defined starting state
   and contiguous selected Bitcoin chain window, with source provenance labeled.
   Implement multiplicity, creation/spend order, maturity, duplicate-transaction
   rules/exceptions, unspendable-output treatment, and necessary value/lock
   checks. Materialize complete survivors and compare their exact contents
   against incremental validation from the same starting state. Include invalid
   double-spend, future-output, same-block order, amount, and duplicate-creation
   cases. A supplied starting state is a bounded test fixture, not a shortcut
   for the final first-launch benchmark.
4. **Then measure the architecture and capacity.** Build a bounded packed or
   disk-backed source index once its identities and schema are correct. Measure
   construction, lookup, replay, state output, CPU, RSS, temporary storage, and
   full completion. Compare the existing script pool on the same workload,
   then the patched/advice candidates with actual multicore scaling and all
   helper costs. Coordinate a quiet resource window; shared-host runs remain
   diagnostic. Keep algorithm/provenance and signature/backend costs separable.

Update experiment 72–75 descriptions and LOG statuses to match what each gate
actually establishes. Keep raw historical results and failures, link corrected
runs rather than rewriting evidence, and use
`cargo test --release -p <affected-crate>` for relevant Rust changes. Protocol
changes still require real connections; these offline tools do not establish
network behavior.

Return a small repair set and updated evidence before a GPU/cluster proposal.
The current data may ultimately support a multi-hour practical outcome on this
laptop, or a better CPU design may reduce it. The immediate need is a correct
workload and a measured implementation limit, with neither promoted to a
physical impossibility claim.
