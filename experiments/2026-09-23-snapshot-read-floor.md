# Experiment: is 20 seconds an unavoidable snapshot startup floor?

Status: complete — prepared-index startup demonstrated; full-scan overlap
inconclusive versus the original baseline. Isolated storage prototype, no
chainstate integration.

Workstreams: W4 (storage), snapshot-assisted startup. Scorecard: P3, P4, Q2.

## Question

The preceding experiment treated a roughly 20-second sparse-index build as the
time to read the entire snapshot and therefore an unavoidable hardware floor.
Test two distinct hypotheses:

1. A full scan has overlapping read and parse work left to exploit.
2. A prepared snapshot can carry an authenticated directory, allowing startup to
   read the directory and authenticate data chunks on demand.

The second changes preparation and verification scheduling. It is not an
equivalent-work claim that an arbitrary, untrusted file can be fully verified
without reading it. Preparation, downloading, semantic snapshot validation,
background historical validation, and later random reads remain real costs.

## Baseline and candidate

Baseline revision: `6470fc2e4308c2124d6f49d4ad461cfc5913c0bd`.

- Baseline: release `snapshot_bench runindex` and a raw sequential read.
- Candidate: [snapshot_floor.rs](../crates/avila-consensus/examples/snapshot_floor.rs),
  a standalone experimental example.
  No existing backend, RPC, consensus rule, dependency, or lockfile is changed.
- `scan`: bounded, checked structural parsing, sparse directory in memory.
- `pack`: the same scan plus SHA-256 for each chunk, a durable index, and a
  deterministic lookup corpus. The default chunk contains 256 complete txid
  groups. The snapshot bytes are retained unchanged.
- `bench`: authenticate the directory against a supplied trusted root, read the
  51-byte snapshot header, and expose lookups. Each lookup reads and hashes its
  exact chunk before returning the encoded coin or proving absence.

The serial and pipelined versions use the same parser. The pipeline uses one
reader thread and a bounded queue of two 8 MiB buffers. This tests overlap
without mmap, unsafe Rust, new dependencies, or parallel agents.

Build: pinned Rust 1.98.1, committed Cargo.lock, ordinary workspace release
profile (thin LTO, one codegen unit, overflow checks). No native-CPU flags.
The runner records source/binary/lockfile hashes and resource counters.

## Workload and measurement protocol

Hardware observed locally:

- Intel Core i3-N305, eight cores, approximately 30 GiB RAM, no swap.
- Samsung SSD 990 EVO Plus 1TB, Linux identifies transport as **NVMe**.
- Negotiated PCIe link: 8.0 GT/s, width 4. A low measured throughput does not
  identify the device as SATA or imply that it has a mechanical disk head.
- Linux 7.0.0-31-generic; source and output on `/dev/nvme0n1p2`; `/tmp` is tmpfs
  and is used only by small tests, not the large storage benchmark.
- Shared desktop with other activity; this is not an isolated hardware maximum.

Dataset: the existing `avila-170m-snap.dat`, **9,314,389,329 bytes**, 170,000,000
coins, 113,331,301 txid groups. It was generated by the repository's
`snapshot_bench gen`, with its fixed RNG seed, counter txids, 1–2 outputs per
group, and mixed scripts. It is **synthetic mainnet-scale data**, not a mainnet
UTXO dump. The base hash is the generator's `[0xab; 32]` placeholder. Counter
txids contain many zero bytes; compression and interpolation results on them
would not establish performance on cryptographic transaction hashes.

Dataset SHA-256:
`4140fa5678e138a3838b486701fa43f402b7fb1c00188bed0d953e6f9a1d8c5f`.
Computing this checksum was a separate untimed-provenance pass, not hidden
inside the reported startup interval.

Every timed cold-advised run calls `POSIX_FADV_DONTNEED` on its input files.
No privileged global page-cache flush is used. Advisory eviction is checked
against physical I/O counters: `/proc/self/io` for Python raw reads and Rust
startup/query phases, and GNU time's block counters for subprocesses. The raw
read reuses one 4 MiB buffer. Tests run separately from timed measurements.

The runner executes serial and pipelined scans in alternating order, records
all repetitions, charges durable preparation separately, then evicts both the
index and snapshot before each open/query run. Lookup targets are captured
during preparation, sampled every 65,536 coins and deterministically shuffled
before timing. It checks the SHA-256 of **every returned coin body**, not just
the number of nonempty results. There are 2,594 lookup samples.

The original benchmark uses ascending sampled queries and returns decoded Coin
objects; the candidate shuffles queries and returns authenticated encoded coin
bodies. Their query rates are not an exact matched-work comparison.

## Results

Initial audit (two runs; raw artifacts in `target/snapshot-floor/baseline.json`):

| Operation | Wall time | Physical reads | Interpretation |
| --- | --- | --- | --- |
| Raw whole-file read | 13.079 s, 11.390 s | 9,314,390,016 bytes each | Approximately 712–818 MB/s; all source bytes came from storage |
| Original index + sampled queries | 23.628 s, 22.968 s | 9.909 GB, 9.898 GB | Index phase printed 22 s each; whole process consumed 11.60 s, 11.18 s CPU |

The 20-second observation was not a demonstrated physical read floor. Even this
basic reader moved the entire unchanged file in less time. This does not
establish a new permanent floor, or say anything conclusive about sustained
durable write throughput.

A control after the candidate runs read the whole file in **11.985 s**, again
with 9,314,390,016 physical bytes read. The original indexer then took 25.233 s
including queries (its rounded index-only timer printed 24 s). Thus the faster
raw-read observations were not confined to a single early run.

Candidate runs, in execution order within each variant:

| Operation | Seconds | Resource/result |
| --- | --- | --- |
| Checked serial scan | 62.388, 35.721, 35.210 | 12.33–13.74 s CPU, at most 47.2 MiB RSS |
| Checked pipelined scan | 55.548, 22.433, 21.002 | 14.29–14.36 s CPU, at most 92.8 MiB RSS |
| Prepare authenticated directory | **23.546**, including file sync | 23.286 s scan; 20.28 s CPU; 122.3 MiB RSS; 39,141,376 physical bytes written including lookup corpus |
| Authenticate/open prepared view | **0.191, 0.142, 0.158** | 38,977,536 physical bytes read each time; no snapshot scan |
| 2,594 shuffled authenticated lookups | 0.915, 0.818, 0.779 | All expected coin hashes match; 65,327,104 physical bytes read each run |

The directory contains 442,701 entries and is **38,957,763 bytes** (37.15 MiB,
0.418% of the snapshot). Startup reads 38,957,814 logical bytes including the
source header — about **239 times fewer bytes** than scanning the snapshot.
The complete open-and-query processes used 76.6–76.8 MiB peak RSS. Lookup
median latency was 266–279 microseconds, p95 428–680 microseconds, p99
1,002–1,648 microseconds. The sample is small relative to the dataset and does
not establish steady-state node performance.

The primary run's **0.16 s median prepared open**, versus the original roughly
22 s index build, demonstrates the intended startup improvement. It requires
the separately measured 23.55 s preparation and an already trusted root.
Preparing and then opening for the very first local use does **not** beat the
old scan. Reuse, producer-side preparation, or construction during a required
download/verified import is the useful deployment scenario.

Three additional cold-advised checks of the final executable opened in
**0.180, 0.250, 0.170 s**, with the same 38,977,536 physical bytes read.
All 2,594 lookup checks passed each time (0.796, 0.642, 0.703 s). Across all
six opens, the range is **0.142–0.250 s**, median **0.175 s**. The raw artifact
identifies both binary versions; the only intervening code change was a
Clippy-suggested iterator change while collecting the benchmark queries.

The scan-only result is not a demonstrated sub-20 s win. Within this prototype,
pipelining beat serial in all three pairs but cost approximately twice the
memory and more CPU. The original parser remains faster in several runs.
Large wall-time variation with relatively stable CPU and full physical reads
prevents attributing all differences to code. All runs, including the 55–62 s
results, are retained; no outliers were discarded.

Local measured directory root:
`9ace12a16b53f2bfa01c32dca7ad26cfc3dfce1a83745dc60d936209a4c7569c`.
This identifies this experimental artifact; it is not a consensus checkpoint.

[All numerical results, source/binary hashes and controls](results/2026-09-23-snapshot-read-floor.json)
are checked in as a small, bounded artifact. Machine-local command transcripts
and the large generated index remain under `target/snapshot-floor/`.

## Directory format and trust

An index has a 75-byte header (versioned magic, complete original snapshot
header, source length, entry count) and 88 bytes per chunk:

`first txid[32] | offset u64 | length u64 | coin count u64 | SHA-256[32]`

The SHA-256 of the entire index authenticates the directory, including the
key boundaries, offsets, lengths, per-chunk hashes, network and base block.
Startup verifies contiguous coverage, ascending boundaries, aggregate coin
count, the source header and length. Chunks are bounded to 64 MiB and the index
to 128 MiB for this experiment. A lookup uses the preceding txid boundary,
reads exactly that chunk (including short final chunks), checks its hash, and
scans its records. I/O errors, truncation and corruption return errors, never
`None` meaning an absent coin. Outputs within a txid need not be numerically
ordered. The entire txid group stays in one chunk.

**A hash from the same untrusted download is not authentication.** There are
two plausible deployment models:

1. Build and retain the directory during an initial **fully verified import**;
   protect the resulting root with trusted local state. Later starts and reads
   can avoid rebuilding the index and still reject changed chunks.
2. Distribute a canonical snapshot directory whose root is independently
   checkpointed, analogous to an AssumeUTXO commitment. This requires an
   explicit, reviewed binding to the expected UTXO state; existing
   `hash_serialized_3` cannot simply be substituted for this directory root.

This prototype implements neither that semantic validation nor checkpoint
distribution. `pack` only checks structural framing, txid order and counts. A
valid directory root does not prove monetary ranges, valid scripts, a correct
base chain, duplicate-output absence, or historical consensus. It also does
not certify that unread chunks are currently available and uncorrupted.
Corruption of untouched chunks is detected when accessed; an operator requiring
all-file integrity before startup still needs a full verification pass.

This follows an established principle, not a new cryptographic construction:
[Linux fs-verity](https://docs.kernel.org/filesystems/fsverity.html) authenticates
file reads on demand using a committed hash tree. The prototype uses a flat
authenticated directory, small enough to load in full. A tree could reduce
startup I/O further at the price of extra lookup reads and implementation work.

## Correctness and limits

The new example has targeted tests for full coin-body agreement with the
existing snapshot decoder, nontrivial VARINT lengths, large scripts, EOF/tail
lookups, out-of-order numeric vouts, present and absent keys, damaged chunks,
changed indexes, truncated files, wrong headers, malformed counts, overflows,
noncanonical CompactSize, short reads, empty snapshots, and serial/pipeline
directory equality.

Validation: all **six** example tests pass; the changed Rust file passes
`rustfmt --check`, and the [Python runner](../tools/snapshot_floor.py) compiles
and completed the full-scale run. Targeted Clippy completes with no warnings
in the new example and 49 pre-existing warnings in the unchanged library.
These are targeted experiment checks, not a full workspace qualification.

Inspection also found limits in the preceding benchmark:

- Its fast VARINT walk omits Core's increment on continuation bytes. A script
  length requiring multiple bytes can therefore desynchronize the walk.
- `SnapshotRun::get` reads exactly 128 KiB even at EOF and treats read failure as
  a missing coin. Large groups/scripts also invalidate a fixed-size window.
- The old sample only counted hits. It did not compare the retrieved contents.
- `runindex` is not the live `Chainstate::load_snapshot` path. The live path also
  checks the expected serialized UTXO hash. Neither the old 20 s figure nor this
  experiment is a measured time-to-usable full node.

Those existing experimental paths are left intact as the benchmark baseline.
The new reader is not installed as the node's storage backend. Mutable overlay,
undo/reorg integration, validated-root persistence, crash-safe publication,
adversarial resource qualification and full-node differential tests remain
integration work.

## Reproduction

```sh
cargo build --release --locked --offline -p avila-consensus \
  --example snapshot_floor --example snapshot_bench
cargo test --locked --offline -p avila-consensus --example snapshot_floor
python3 tools/snapshot_floor.py /path/to/avila-170m-snap.dat \
  --output target/snapshot-floor/new-run --repetitions 3
```

The output directory must not exist. `results.json` contains commands, all
measurements, hashes, environment and resource counters. `snapshot.idx` and
`snapshot.idx.queries` are durable experiment artifacts. The snapshot itself
is opened read-only. Large datasets and generated indexes stay out of Git.

To recreate the synthetic dataset, use the existing `snapshot_bench gen`
command, with a fresh `SNAP_BENCH_DIR`, a new output path and count 170000000.
Dataset generation is separate from the measurement interval.

## Further experiments

- Build the directory while downloading/exporting the snapshot, and compute
  the required semantic commitment in the same pass. Count that work in the
  transport/import stage rather than performing another full disk scan later.
- Use independently compressed, authenticated chunks to reduce transfer and
  storage bytes while preserving random access. [Zstandard's seekable format](https://github.com/facebook/zstd/blob/dev/contrib/seekable_format/zstd_seekable_compression_format.md)
  supplies independently decompressible frames and a seek table; its optional
  short checksum is not a substitute for the cryptographic commitment here.
  Compression must be measured on real txids, not counter-heavy fixtures.
- Vary chunk size and index density against cold random-read latency and memory.
  An immutable base plus a small durable mutable overlay is the natural storage
  integration, but its recovery and reorganization behavior require testing.
