# Experiment: where does connect_block time actually go?

**Date:** 2026-09-23 · **Status:** adopted — answers the storage-layer stakes question
**Artifact:** `connect::ConnectTiming` (relaxed-atomic phase buckets),
`examples/connect_bench.rs`, `tools/make_spend_fixture.py`

## Question

Every prior experiment optimized the UTXO layer without ever measuring
its share of end-to-end validation. This experiment prices it.

## Setup

Workload: 625 regtest blocks, 15,989 txs (~26/block), real wallet-signed
P2WPKH spends — genuine ECDSA checksig work, generated by a Knots
regtest daemon (`make_spend_fixture.py`; spread-funding via `sendmany`
so every input is confirmed — no mempool chains).

Harness: `Chainstate::with_store_coinsdb` (full persistent path) +
`accept_header`/`accept_block` per block. Phase buckets via
`Instant` timers inside `connect_block`: `read` (check_tx_inputs UTXO
fetches), `apply` (spend + add_tx_outputs), `scripts` (parallel
sigcheck drain), `bip30`, `total`.

## Result — identical on both engines

| phase | redb | hash | share |
|---|---|---|---|
| scripts | ~3.2 s | ~3.2 s | **~95%** |
| apply | ~110 ms | ~90 ms | ~3% |
| bip30 | ~42 ms | ~52 ms | ~1.4% |
| read | ~17 ms | ~17 ms | ~0.5% |
| other | ~9 ms | ~9 ms | ~0.3% |

206 vs 205 blocks/s — engines indistinguishable. At 512 MiB *and*
32 MiB budgets: **zero backend commits** — the dirty map absorbs the
entire workload (16k coins ≈ 1.3 MB dirty).

## Conclusion

**Per-block validation is script-check-bound, not storage-bound.**
UTXO reads+writes are ~3.5% of connect time when the working set fits
the cache — which at this density it always does.

Consequences for the program:

- The hash engine's wins (ingest, commits, disk footprint) stand, but
  they are *capacity/ingest* wins, not per-block latency wins.
- The disk-bound regime exists only when dirty churn exceeds the
  budget — i.e., deep-UTXO IBD (170M+ set vs 450 MB cache). It is
  not measurable at this scale; a real-disk deep-set sync is the only
  honest test, and it's the same test the hash engine needs anyway.
- The largest remaining wall-clock lever is **cross-block script
  overlap** — validate block N+1's sigchecks against the post-N
  overlay while N's commit lands. `run_script_checks` is already
  parallel within a block; extending it across blocks targets the
  dominant 95% bucket rather than the 4% one.
