# Experiment: does one-byte ECDSA advice survive real Script execution?

Status: measured prototype in an isolated workspace; no production integration.

Roadmap: W2 validation speed, W3 synchronization hints. Scorecard: P1 partial
replay evidence, C1/C2 compatibility and hostile inputs, P5 helper costs.

## Question and hypothesis

The [signature-kernel experiment](2026-09-23-ibd-ecdsa-advice.md) measured 1.82x
CPU throughput with one byte of nonce-point advice. Does enough survive actual
DER parsing, sighash computation, Script execution, hint handling and local
worker communication to justify more engineering?

The decision threshold is a substantial reduction, approximately 20%, in matched
replay time with the same rule coverage in each arm. Full mainnet IBD requires
additional evidence; it must not be inferred from either workload below.

## Profiles, baseline and candidate

The source baseline is this repository at the Git revision in the manifest,
with its locked dependencies and Rust toolchain. The runner copies the workspace
under `target/ecdsa-replay/` and makes three explicit experimental changes there:

1. Add the [lab hook](code/ecdsa_replay_hook.rs) and
   [replay driver](code/ecdsa_replay.rs).
2. Route the ECDSA verification method through the hook, retaining the original
   method as the ordinary verifier and fallback.
3. Use one Script execution thread in both arms, making the sequence of check
   attempts deterministic for the one-byte stream.

The baseline performs ordinary local verification. The candidate receives a
prepared hint stream and synchronously sends batches of up to 8,192 locally
derived signature/key/digest tuples to a
[local arithmetic worker](code/ecdsa_advice_worker.c). This worker uses the
unchanged, previously measured native kernel. It is a trusted local executable
performing verification, **not** the untrusted external hint supplier. Process
CPU accounting includes both the Rust process and the child it waits for.

The C worker reparses compressed public keys after the Rust hook has parsed the
original keys. This duplication and all pipe communication are charged to the
candidate. No zero-overhead integration is assumed.

No production Rust source, Cargo manifest, dependency version, application
configuration or running node is changed. The copied workspace still forbids
unsafe Rust. This is a Linux research harness with private libsecp APIs, not an
approved cryptographic interface for deployment.

The repository changed concurrently during the experiment. The authoritative
copied build records revision `ce7f60ea92d91817c0ef9e98d693b0ffb097ee57` and hashes
every staged Rust source. Both arms use the same measured binary. The later Git
HEAD captured by the run is not used to identify that binary's source.

## Preserving Script semantics

A valid block can contain signature attempts that return false. In particular,
multisig tries candidate keys, and a script may use the boolean result in later
operations. A batch of all attempted checks cannot simply require all to pass.

The producer records an ordinary execution trace and reconstructs nonce hints
from its public tuples. It emits a byte `0..3` for a true ECDSA check and a
sentinel `255` otherwise. The producer's classification is checked against the
ordinary Rust verifier during preparation. This is preparation correctness
evidence; the recipient does not trust that classification.

The recipient runs the original interpreter and computes the original sighashes:

- A true hint queues the locally derived tuple and provisionally returns true.
- A false, invalid or missing hint invokes ordinary local verification and uses
  its actual boolean result. Claimed false results are never trusted.
- Fresh random coefficients are generated by the local worker only after all
  records of a batch have been received. Every hinted true result must satisfy
  the checked batch equation from the earlier experiment.
- A failed batch, worker failure or speculative replay error discards the
  provisional replay and repeats the workload using ordinary verification.
- No result is printed as accepted until all pending checks have completed.
  No provisional state is persisted or served.

If the queued true checks are valid, every boolean supplied to the interpreter
matches ordinary execution, so its path and outcomes match. This retains the
earlier experiment's probabilistic batch-acceptance guarantee, not deterministic
equivalence for every possible random draw. Tests do not replace cryptographic
review. The whole-workload retry is deliberately simple and can be expensive;
production would require bounded rollback windows and a policy to abandon bad
advice sources.

## Workloads and method

### Recent mainnet Script replay

The [corpus extractor](../tools/ecdsa_replay_corpus.py) reads public `blk`/`rev`
files and their public XOR obfuscation key from the existing local Core data
directory. It does not open wallets, credentials or writable node databases.
Physical block files contain out-of-order downloads and gaps; the extractor
chooses the first sufficiently long linked run in the selected file.

The sample is **24 linked blocks, heights 956105–956128**, containing **99,198
non-coinbase transactions**. Original serialized blocks plus undo payloads occupy
**44,568,279 bytes** in the experimental corpus. The manifest records every block
hash, payload hash, source-file hash and offset. Undo records are matched by their
stored checksum over the parent hash and undo payload, following
[Core's block storage](https://github.com/bitcoin/bitcoin/blob/v29.0/src/node/blockstorage.cpp).
The decoder follows [Core's undo serialization](https://github.com/bitcoin/bitcoin/blob/v29.0/src/undo.h),
including its historical dummy version field.

Both arms decode blocks, run context-free block checks, check the sample's header
linkage, decode undo outputs and execute every non-coinbase input script under
the original height-dependent flags. DER handling, high-S normalization, legacy
and witness sighashes, and unaccelerated Schnorr verification remain in the
existing code. The final digest covers the block hashes and successfully checked
transaction witness IDs; it is an outcome digest, not a UTXO-state commitment.

**Scope limit:** undo is locally supplied prestate. Its storage checksum is not
a consensus commitment to historical coins. This workload does not derive that
prestate, validate the complete header ancestry or execute all contextual state
transition rules. It is historical Script replay, not full mainnet IBD.

### Complete test-chain and early-mainnet replay

The existing spend fixture is replayed from genesis through `Chainstate`, with
headers, block acceptance, contextual/UTXO rules, Script checks and the complete
final UTXO hash. The candidate is compared with the ordinary verifier's final
`hash_serialized_3`, coin count and accepted block/transaction counts. No snapshot
or assumed-valid state is used for this workload.

The committed mainnet heights 0–500 fixture is also replayed from genesis. It
adds actual early uncompressed-key/high-S history but is too small and sparse
to establish a useful speedup. Its regressions remain in the results.

These two replays use an in-memory chainstate. Disk persistence, database cache
pressure, network transfer and reorganization performance are not measured.

### Timing and resource accounting

- Three measured repetitions per arm, alternating baseline/candidate order.
  No samples removed. Report median and full min/max range, not confidence bounds.
- Existing i3-N305 desktop under shared load. One Rust Script thread; the local
  C worker runs synchronously. This does not establish an eight-core gain.
- Replay wall time includes hint-file loading, worker startup, all replay work,
  the final batch drain, worker shutdown and any retry. Reading the corpus file
  into memory occurs before that wall timer in both arms.
- Combined process-tree CPU is measured by the Python parent's child-resource
  accounting. It includes the Rust process and the local C child it reaps,
  including process startup and corpus-file reading.
- Producer trace capture and nonce generation are measured separately. The
  current producer performs an ordinary replay followed by a separate point
  reconstruction pass; it does not fuse the two operations.
- Native scratch capacity is 16 MiB and a verification batch holds at most
  8,192 records. The entire hint stream is loaded, capped at 32 MiB. Whole-node
  peak memory, cold storage, energy, actual hint transport and availability are
  unmeasured.

## Correctness and failure evidence

The [Script cases](code/ecdsa_replay_cases.rs) include a valid check, a genuinely
invalid signature, a valid `CHECKSIG NOT` script using a false check, 1-of-2
multisig with a failed key match, uncompressed and hybrid public keys, high S,
malformed DER used as a false result, and lax-DER trailing data. Expected ordinary
Script outcomes are checked independently of the candidate. The cases execute
ten ECDSA attempts, four of which return false.

For each workload, the runner checks the ordinary/candidate result digest and
check counts, confirms that every supplied true hint was actually queued, and
requires no retry with correct hints. Hostile/missing-hint variants include:

- A wrong nonce parity that remains a plausible curve point, forcing a failed
  batch and complete ordinary retry.
- A false-result claim for a genuinely valid signature, which must use the
  actual ordinary result.
- A missing hint-stream tail, which must use ordinary checks.
- A forged true claim for a false attempt, and true claims for all false
  attempts where available, which must preserve final Script outcomes.

The local worker's earlier cancellation, invalid-input and rare `x=r+n` tests
also run under libsecp VERIFY, AddressSanitizer and UndefinedBehaviorSanitizer.
LeakSanitizer is disabled because the managed runner uses ptrace. These tests
share the baseline's arithmetic library and do not prove consensus equivalence
across all history.

Additional checks passed after the timing run: nine protocol cases under
ASan/UBSan/VERIFY on 256 actual historical tuples, the same nine cases on the
ten Script-fixture tuples, and ten existing Rust signature-checker tests in the
isolated workspace. The protocol cases compare native and Rust results and
reject altered digests, wrong nonce signs, unknown commands, zero/oversized
counts and truncated records. An exiting local worker forced ordinary retry;
an empty hint stream executed every check ordinarily. Both retained the exact
regtest UTXO hash. Those extra recovery checks ran alongside compilation and
sanitizer tests, so their timings are correctness diagnostics, not performance
comparisons.

## Results and decision

[Published measurements, source manifests and correctness results](results/2026-09-23-ecdsa-historical-replay.json)
retain all 40 registered replay runs, including small-workload regressions and
hostile hints. No outliers are removed. Reported source and binary hashes were
verified against the measured files after testing.

**Median elapsed seconds [min, max], three repetitions:**

| Workload | Ordinary | One-byte advice | Median time reduction |
| --- | ---: | ---: | ---: |
| 24 recent mainnet blocks, Script replay | 27.650 [25.907, 27.680] | 18.408 [17.172, 19.947] | **33.4%** |
| Complete 625-block spend fixture | 6.170 [6.070, 6.335] | 4.221 [3.954, 5.595] | **31.6%** |
| Mainnet genesis through height 500 | 0.01202 [0.01200, 0.01226] | 0.01477 [0.01368, 0.01499] | **22.9% regression** |

**Median combined process-tree CPU seconds [min, max]:**

| Workload | Ordinary | One-byte advice | CPU reduction |
| --- | ---: | ---: | ---: |
| Recent mainnet Script replay | 24.567 [24.297, 24.977] | 17.431 [16.373, 17.504] | **29.0%** |
| Complete spend fixture | 5.518 [5.504, 5.670] | 3.794 [3.739, 3.860] | **31.3%** |
| Early mainnet | 0.01341 [0.01338, 0.01353] | 0.01483 [0.01456, 0.01507] | **10.6% regression** |

The mainnet workload executes **183,782 ECDSA attempts**, including **6,137
false results** inside valid scripts. The candidate batches the **177,645 true
checks** and verifies every false attempt ordinarily. All three candidate runs
have the same trace count and result digest as the baseline, with no retries.
The trace contains 271 uncompressed-key checks; no hybrid or high-S checks were
observed in this recent sample. The synthetic cases cover both, and the early
mainnet trace contains ten uncompressed-key checks, three with high S.

The complete spend fixture has **15,989 transactions and 43,032 ECDSA checks**.
Every ordinary/candidate and failure-case replay finishes with **12,995 coins**
and the same `hash_serialized_3`:

```text
e5b0e2cbfffc9137ec750d631f05ad5d9bb74d0fba47be2f35c552c252633707
```

The 501-block early-mainnet replay has only ten ECDSA checks and ends with 503
coins. Worker startup and framing overwhelm the small amount of shareable work.
This is a measured reason to keep ordinary verification for small workloads.

### Helper costs and failure penalties

The recent-mainnet hint stream is **183,782 bytes** (about 179.5 KiB), including
false-result sentinels. No bit packing, network protocol or per-transaction
framing is implemented. The current stream assumes the matched serial execution
order; parallel or interoperable delivery needs an explicit association format.

Current preparation costs are **29.781 s** for ordinary replay plus trace
capture and **27.398 s** for the native point-generation pass: about **57.18 s**
before any recipient replay. The corresponding measured CPU is 27.102 s for
capture and 22.287 s inside the point-generation worker; the latter excludes its
Python controller and process initialization. The generation wall timer also
excludes loading the already written trace into memory. This producer is a
two-pass prototype, not an optimized fused producer.

For one fresh node creating its own hints, preparation plus recipient replay
costs roughly **75.6 s**, versus **27.7 s** ordinary replay in this sample. The
gain relies on prepared advice being reused; it is not a reduction in first-use
work for a lone node making its own advice. Capturing the nonce point during an
existing verification could reduce producer duplication, but is unimplemented.

**Recent-mainnet failure workloads, one measured run each:**

| Hint condition | Elapsed seconds | Ordinary retry | Result |
| --- | ---: | --- | --- |
| One wrong nonce parity | 61.657 | Yes, entire sample | Matches baseline |
| One false-result claim for a valid check | 20.075 | No; that check verified ordinarily | Matches baseline |
| Missing second half of hints | 25.036 | No; missing checks verified ordinarily | Matches baseline |
| One forged true-result claim | 55.034 | Yes, entire sample | Matches baseline |
| Every false-result sentinel replaced by a true claim | 53.394 | Yes, entire sample | Matches baseline |

The first row is more than twice the ordinary median. The simple whole-replay
retry protects correctness in this prototype but is unsuitable as an unbounded
production recovery policy. Missing hints also still incur extra canonicalization
in this implementation before the ordinary check; a production bypass should
avoid that work when no advice is available.

**Decision: continue to a parallel, bounded-window replay prototype.** The
approximate 20% threshold was exceeded on both the recent-mainnet Script
workload and the complete spend-fixture replay, including recipient hint
handling. The gains reduce measured recipient CPU and elapsed time through
completed verification; they are not startup-only or deferred-work measurements.

The threshold for **full mainnet IBD** remains untested. Before adopting this
architecture, measure an eight-core implementation with explicit per-transaction
hint association, bounded pending work and rollback, persistent chainstate,
larger historical/activation coverage, helper absence/corruption, and external
cryptographic review. A gain in this single-thread profile is not a guaranteed
gain over the existing pooled validator on eight cores.

## Reproduction

The local Core block-file number is installation-specific. The recorded corpus
hash and per-block hashes identify this sample; choosing another physical file
produces a different workload. Large chain/trace data and binaries remain under
`target/`, outside version control.

```sh
python3 tools/ecdsa_replay_corpus.py \
  --blocks-dir /path/to/bitcoin/blocks --file-number 5625 --count 24 \
  --output target/ecdsa-replay/new-corpus

python3 tools/ecdsa_replay_bench.py \
  --historical-corpus target/ecdsa-replay/new-corpus/corpus.bin \
  --chain-corpus /tmp/spend-fixture.dat \
  --output target/ecdsa-replay/new-run --repetitions 3
```

The runner uses cached, locked dependencies and records source/build hashes and
all samples. The spend fixture was generated by the existing
[`make_spend_fixture.py`](../tools/make_spend_fixture.py); its measured checksum
is recorded. Build-only and reuse-build options support development; reuse
rejects changed experiment sources. A complete run includes corpus preparation
as a separate step and publishes its costs separately from recipient replay.
